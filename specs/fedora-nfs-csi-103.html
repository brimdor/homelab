Native Fedora NFS CSI container domains

Remaining software acceptance

The accepted native NFS profile exercises host kernel clients, while the accepted CSI4.13.5 consumer profile uses Ubuntu ARM64. Neither proves ordinary container SELinux domains on the candidate Fedora AMD64 host. The combined Kured fixture installs signed vendor policy and verifies enforcing mode and the K3s process domain, but its service does not explicitly enable containerd SELinux. Those results remain valid within their recorded scopes.

Selected bounded profile

Add a separate, repository-owned subclass of the existing signed Fedora44 kernel fixture. Reuse its exact cloud/DVD/kernel hashes, strict pre-generated SSH trust, disconnected QEMU transport, primitive checks and signed kernel install/rollback/return. Reuse the reviewed K3s1.33.6 AMD64 binary and airgap hashes, signed k3s-selinux1.6 EL9 package and vendor installer binary context. Enable K3s --selinux with its default data directory. Verify the generated containerd setting and actual CRI process domains; enforcing host mode alone is insufficient.

Use one actual native K3s node, its default Flannel networking, and the exact previously reviewed NFS CSI4.13.5 chart. Resolve and record the five official images' Linux AMD64 child manifests and original index digests, plus the existing immutable Python consumer image. Copy only those exact public images to owned OCI archives using installed Skopeo, verify every OCI blob, and import through native containerd. No registry credentials, public network access from the guest, production API, existing data, NAS or Tailnet participate. No image build is required.

Acceptance and refusal checks

  1. Install only signed offline nfs-utils/container-selinux and the exact signed vendor K3s policy. Record policy/RPM identities, booleans and enforcing state. Do not set permissive mode, add custom allow rules, relabel NFS data, change booleans, or grant consumer privileges to obtain a pass. A supported policy change, if actually required, needs its own recorded source diagnosis and desired-state revision.
  2. Start the default-data-directory K3s service with explicit SELinux support and the already reviewed inert airgap gateway. Require one Ready node, native kernel7.2.11, immutable imported image digests, and a fresh synthetic cluster UID. Render the exact chart with snapshots and StorageClasses disabled, mountPermissions0, File fsGroup policy and immutable images. Preserve upstream security contexts and require complete controller and node-plugin readiness.
  3. Export only a new owned loopback NFS4.1 tree with root squash. Prepare a Builder directory root0:1000 mode2770 and UID1000 marker mode0600, a deliberately incompatible root0:0 mode0755 directory, and a backup directory65534:65534 mode2770. Create separate static Retain CSI PVs/PVCs on this disposable server; require exact PV/PVC UIDs, claimRef UID, share and driver identities. No dynamic permission repair or production adoption.
  4. Run ordinary consumers with RuntimeDefault seccomp, dropped capabilities, read-only root, no service account token, actual UID/GID1000 and fsGroup1000/OnRootMismatch. Bind each observed native process PID to the exact live Pod UID and CRI container ID. Require container_t for consumers and record every CSI container domain, including the upstream privileged plugin. Require actual NFS4.1 hard mounts and preserve existing metadata. Two same-node consumers of the same claim must exclude nonblocking locks and each append100 fsynced records under locks; compare all200 complete records and exact bytes, not a readiness-only check.
  5. Require write denial and unchanged metadata for the deliberately incompatible directory if its consumer starts. Root/no-fsGroup backup writes must be squashed to65534:65534. Recreate the good consumer, verify a new Pod UID, its actual container domain, and all corpus bytes. Restart the owned CSI node Pod, verify replacement UID/readiness and repeat complete corpus readback and a fresh locked write.
  6. Retain compact asset, signed kernel, native policy, runtime domain, mount, identity, corpus and refusal evidence. On failure retain bounded synthetic diagnostics, including relevant AVCs, without tokens or kubeconfigs. The tracked parent stops/reaps exact owned processes and deletes the whole VM, images, exports, mounts, credentials, synthetic data and caches in finally. Independently match the exact QEMU executable and root-drive argument before declaring absence.

Limits and parent completion

This profile targets the current K3s1.33.6 baseline and the candidate Fedora44/kernel7.2.11 host. It does not prove future K3s versions, Cilium on Fedora, multi-host NFS coherence, live lock reclaim, Ceph CSI, physical GPU operation, actual NAS exports/permissions, protected data recovery, migration or a permitted production rollout. The already accepted independent HA/Cilium and NFS profiles retain their own scopes. NAS restrictions, deferred owner actions, exact release gates and final-only credential rotation remain unchanged. Issue103 remains open until all required live completion gates are met.
