Native Fedora44 Ceph kernel client qualification

Contract and supported scope

Issue103 CEPH_SECURITY requires client compatibility and intact data through supported patch/key changes. A1 and K3S_CILIUM also need native Fedora/kernel evidence. Existing modern-only RADOS and Rook acceptance does not establish kernel authentication. Official Fedora44 update metadata, collected by fedora44-current-ceph-package-metadata-15x5sofr at2026-10-23T02:29:01UTC, lists signed-package candidates for Ceph20.2.4. Rook requires kernel7.0 or newer for AES256K kernel clients; the separate 7.2.11 boot/rollback qualification is the prerequisite. Package metadata is not proof of a valid RPM signature or successful boot.

Plan before implementation

  1. Reuse the exact signed Fedora44 media, restricted QEMU, pinned synthetic SSH, native enforcing policy and kernel driver's real installation/boot/rollback checks. Keep every original refusal and cleanup boundary. No production host or NAS mutation.
  2. Read only official Fedora44 Everything and updates metadata over trusted HTTPS. Verify every metadata hash against its repomd, every chosen RPM against its primary metadata, then every native RPM signature against the key already supplied by the verified Fedora44 cloud. Refuse foreign URLs, unsafe paths, unknown hashes, NOKEY and changed versions. Preserve the complete metadata only during its named active fixture.
  3. Transfer metadata into the disconnected guest. Use the native DNF5 dependency solver with download --resolve --url, without network access or installation. Transfer only the exact metadata-bound selected RPMs. Install only the exact Ceph20.2.4 targets and their solver-selected dependencies with signature checking and weak dependencies disabled. No unrestricted guest egress, unsigned package, certificate bypass or production repository change.
  4. Reuse the reviewed native modern-only Ceph runtime's monitor, manager, single synthetic BlueStore regular file, RADOS bytes, same-file restart, core/admin rotation and retired-key refusal. The new VM-specific entry must independently require the exact synthetic hostname, Fedora44, kernel7.2.11, root, SELinux enforcing, no production/public route, no existing Ceph state and a private owned /work. Do not relax the existing capability-free container entry or permit legacy cipher creation.
  5. Create only a new synthetic RBD image and a new AES256K client. Require no preexisting mapped RBD devices; verify the native map identifies exactly the owned pool/image before writing. Write deterministic bytes through the kernel device, fsync and compare the entire written region after unmap/remap, key rotation and fresh remap. Require the retired key's explicit authentication refusal and no residual mapping. Do not format or access an unknown device. Preserve RADOS bytes and all synthetic cluster/block identities.
  6. Stop/reap every owned Ceph process before the parent destroys its owned VM. Remove all owned media, RPMs, metadata, keys, controller and caches after success, failure or cancellation. Retain only compact sanitized source/hash/result/cleanup receipts.

Limits and actual gates

This independent fixture targets native kernel RBD authentication, persistence and fresh client-key rotation only. It does not establish CSI provisioning/attach/snapshot, CephFS, legacy AES service-ticket transition, multi-host replication, production recovery, SATA isolation, firmware, GPU or OS release migration. Those remain separate checks. The existing Rook safeguard disabling the optional manager backend on20.2.4 remains intact. No warning muting, emergency cipher override, legacy creation retry, production key import or NAS operation is allowed. Any software failure remains agent-owned diagnosis; only evidenced human/physical/security gates stop the affected step.
