Maintenance #103 · 2026-10-19 · GRAFANA_SQLITE_STARTUP

Retry transient SQLite startup contention

Candidate mitigation, pending exact live acceptance. A successful startup proves that rollout; it cannot establish that every future scheduling of an intermittent race is fixed.

Evidence and causal limits

Grafana 12.3.1 logged a database-locked error from its one-time service-account migration at 2026-10-19T11:51:25Z. Provisioning files and both sidecars passed their checks. The earlier one-connection pool candidate stalled schema migration and was reverted by 4fbf18c54e53b3e339eda0f5759c572c2ca12f31; that pool change is excluded.

Exact 12.3.1 lock code performs a transactional get/create followed by a nontransactional update before invoking the migration callback. Its query wrapper and transaction wrapper implement SQLite lock retries. The original error does not identify which lock stage failed. Transaction commit errors are not retried by that wrapper; this candidate does not claim otherwise.

Desired state

  • Set database query_retries=10 and transaction_retries=20, using documented SQLite controls. The query path has bounded exponential backoff; the transaction callback rolls back before retrying. SQL execution time is additional to retry sleeps.
  • Set only readiness initial delay to 15 seconds. Preserve the readiness endpoint and failure thresholds, all liveness settings, default connection pool, private cache and journal mode.
  • Enable debug for infra.lockservice only. Source shows action names and execution boundaries; SQL logging and global debug remain disabled. This gives positive evidence that the startup callback ran.
  • Preserve chart 10.5.15, Grafana 12.3.1, sidecar 2.14.1 digest, credential references, OAuth configuration, resources, services, ingress and storage. Existing data storage is emptyDir; restart has the existing ephemeral initialization semantics. No persistent-data migration or direct database operation is introduced.

Validation and rollout

  1. Capture current Deployment/Pod/image identities, storage definition, container status, public unauthenticated health, both sidecar health endpoints and all provisioning file hashes. Do not retry denied authenticated login.
  2. Render baseline and candidate by resource identity. Permit only the INI ConfigMap content, its Deployment checksum, and readiness initial delay. Parse the INI and compare every other field. Run Helm lint, targeted pre-commit and API server dry-run.
  3. Commit and push to canonical Gitea master, immediately refresh Argo, and verify exact revision sync/health and rollout.
  4. Require the one-time migration's lock start/execution/finish records and no service-account failure, fatal, database-locked exhaustion, authentication denial or provisioning error. Require all containers ready with zero restarts, unchanged runtime image IDs, both sidecar health endpoints, identical provisioning hashes and healthy public API.
  5. Observe the same Pod beyond its initial liveness evaluation window. Preserve original warning events and CORE output. Do not infer authenticated datasource/OAuth behavior from public health or file hashes.

Failure and rollback

If startup or functional checks fail, revert the exact candidate commit through GitOps, refresh Argo and prove restored readiness/health. Capture sanitized failure evidence. If public access is denied, stop that interface without alternate paths; record the access gate and distinguish it from application failure. Never restore the failed single-connection setting, enable WAL as a shortcut, weaken liveness, query SQLite directly, rotate credentials or use another identity.
