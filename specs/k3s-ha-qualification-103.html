Plan and acceptance checkpoints

  1. Validate source offline, publish exact files to canonical Gitea master, then create the empty private VM. Inspect actual no-mount configuration and native kernel/BTF. Use the VM's measured inherited resolver in a guest-owned read-only resolver file passed through K3s --resolv-conf; never guess a resolver or repeatedly patch generated CoreDNS after upgrades.
  2. Create exactly three servers and two agents at the pinned baseline image. Verify loopback Kubernetes endpoint, nonproduction namespace UID, exact node names/UIDs, private container IDs/configuration/volume identities and matching kubelet versions. Disable flannel, kube-proxy, network policy, bundled ingress/ServiceLB/local storage/metrics and Helm controller. Enable secrets encryption. Install fixed Cilium 1.20.3 with native cgroup root and Hubble.
  3. At baseline and every accepted upgrade/rollback/return: require all five nodes Ready without pressure, exact per-node kubelet versions, five ready native Cilium agents, required DNS answers, four official strict-flow allow/deny/L7 cases without required skips, and external synthetic ARP plus ten exact application HTTP payloads before and after L2 lease transfer. Preserve synthetic pool, Service and namespace identities. No production L2 claim.
  4. Before each transition, write a public synthetic marker, create an embedded-etcd snapshot, record nonzero size/digest and confirm the original server token file exists without reading it. Change the marker afterward. Replace only the exact owned container's K3s binary by verified digest and atomic rename. Restart one server at a time, proving both surviving server APIs and etcd readiness plus an actual committed synthetic API write while it is stopped; then upgrade agents one at a time. Preserve container IDs/configuration/mounts and Kubernetes node UIDs. Check app response after each restart.
  5. After each upgrade, drain only the five synthetic nodes, stop all five owned containers, install prior binaries while stopped, then restore the matching-version snapshot using a temporary owned helper attached only to the original synthetic data volumes and original token file. Never start an old binary against a newer datastore without restoration. After restoration, remove only stopped peer servers' exact synthetic database directories and rejoin peers, then agents. Verify the pre-snapshot marker was restored and post-snapshot mutation disappeared. Rerun full acceptance, then return through the same forward sequence and repeat acceptance.
  6. On any regression stop the transition before another node; fix ordinary source/fixture errors through another validated publication. Preserve failed evidence. A caller-owned finally path removes exact helper/client/node containers, VM, images, downloaded binaries, synthetic snapshots, private kubeconfig, processes and scratch. Retain compact sanitized commands/results and cleanup receipts only.

Boundaries and limitations

Always: verify ownership immediately before every mutation; keep synthetic credentials inside private scratch/VM and never persist raw restore logs; use compatible kubectl clients, exact hashes and strict acceptance. Separate approval remains required: production disruption, active-data migration, actual security changes and protected application releases. Never: touch production nodes or NAS data, use a real kubeconfig in the fixture, weaken TLS/SELinux, retry the denied Fedora policy/package path, use host mounts, skip required failed cases, publish credentials or revoke the incident PAT before the final maintenance step.

A container restart kills that node's pod processes; it does not reproduce service-only restart continuity. Original container image metadata remains the pinned baseline while measured running binaries/runtime versions change. This fixture uses the container default snapshotter; production's declared stargz configuration remains unqualified. This fixture cannot certify Fedora 44 SELinux policy, production AMD64/GPU/CSI, physical networking/kube-vip, host boot/drain behavior, NAS backup recovery or the Sprigatito SATA incident. The separately accepted Cilium bridge remains necessary. A pass advances a prerequisite, leaves K3S_CILIUM open and does not make all six production layers GREEN.
