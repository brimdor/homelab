Minimal component and contract

Add metal/scripts/maintenance_hop_journal.py as a library only, with no mutation CLI, package command, Node action or automatic release. Reuse the actual global Ownership and host Hold interfaces. A journal can be initialized only after exact global ownership, matching source/target/node/revision, the host's durable owner identity, installed actor guards and native idle conditions pass. Preserve the original global ownership and host marker; no unrelated actor or application state changes.

Use the host's existing private maintenance state directory, an exact owner-token subdirectory, the existing host controller flock, immutable0600 numbered records, canonical JSON, prior-record SHA256 and durable file/directory fsync. Validate directory ownership/mode/ancestry and every record's ownership/mode/type/link count/canonical bytes/sequence/hash chain/schema. Unknown files, malformed/truncated records, replaced host or global ownership refuse. A source or target change needs a new separately reviewed owner and journal; never reinterpret an old hop.

Record each explicit step in strict order: cordon, drain, source preparation, next-release download, offline transaction, trusted reconnect, infrastructure verification, scheduling restoration and application acceptance. Each step first commits an intent containing the exact reviewed input SHA256 and prerequisite-evidence SHA256. The journal never invokes an operation. Only after a caller separately observes the intended result and accepts current identity/health/availability can it append a completion binding that intent and an immutable receipt SHA256. The only operation while an intent remains pending is observation or explicit acceptance/refusal; beginning that or another step fails. Process death, lost response, failure or cancellation never replays commands, releases ownership or uncordons. There is no automatic rollback, retry or success inferred from elapsed time.

Integration and limits

The journal is one safety component, not an executable release workflow. Its callback is a verification boundary, not proof of a real package plan, availability, recovery, GPU/CSI, Fedora transaction or production approval. A future reviewed controller must bind actual native DNF transaction identifiers and offline boot evidence to these digests, implement exact one-node evictions and OS commands, revalidate each phase's real acceptance gates, and explicitly release the actor/global owners after final safe-release checks. No production journal or ownership is acquired during qualification. Test synthetic data only.

Qualification plan

Focused tests integrate the existing ownership/actor implementations with controlled API/systemd fixtures: strict phase order, changed global/host/revision refusal, rejected prerequisite/completion retention, corrupted/foreign/truncated files, lost-response observation, independent-controller resume, real child death after durable intent and native cross-process flock/race exclusion. Run on native Linux using only a private owned synthetic directory and RAM source modules, then verify children reaped and scratch removed. Reuse exact source hashes and publish validated files to Gitea before any later live use. Native filesystem/process tests prove the exercised persistence contract, not power-loss guarantees or a complete production controller.
