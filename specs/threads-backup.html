Threads scheduled backup

Approved scope: maintenance #103, THREADS_BACKUP_COVERAGE. Execution plan recorded before implementation as threads-backup-ej_nl_l8. This specification does not approve a database migration.

Objective and evidence

Close the observed Threads backup gap without restarting PostgreSQL or changing its existing backups. The live server is PostgreSQL 17.5; Threads occupies 7,496,207 bytes. Existing scheduled dumps cover four other prefixes. The backup export has 11,047,776,256 KiB available. These are dated observations from 2026-10-19, not capacity guarantees.

Design and ownership

Add a CronJob and ConfigMap under apps/postgres. Use the exact retrievable running server image digest, whose pg_dump and pg_restore clients are both 17.5. Keep every existing rendered resource unchanged. The Job connects through the existing PostgreSQL Service with existing Threads Secret references; it never mounts PGDATA or a PVC.

Run every ten minutes, forbid concurrent runs, exclude sprigatito, and remove completed Job mounts after sixty seconds. A five-minute Job deadline bounds a stuck backup; it is not an overall maintenance deadline. Disable service-account token mounting, privilege escalation and capabilities; use a read-only container root filesystem.

Store real backups only in the existing durable NAS export, /mnt/user/postgres_backups/db/threads. Never export records or credentials into local evidence.

Publication and retention

Create a private, explicitly owned directory and temporary work. Require successful warning-free pg_dump, a nonempty custom archive and warning-free pg_restore listing. Publish a complete archive using a no-clobber hard link, then its SHA256 and ownership sidecars. Fail without publishing on dump/listing failure. Preserve a published archive if a later stage fails.

Retain fourteen days of generations. Remove only exact-name, owner-marked expired archive/checksum/owner triplets whose checksum still matches. Preserve and report unowned, malformed, symlinked, incomplete or corrupt candidates. Never delete another database's backups. Remove only the current attempt's temporary directory on exit.

Verification and boundaries

  • Test successful private publication, dump/warning/list failures, collisions, retention, checksum/path tampering, foreign ownership and symlinks with synthetic clients.
  • Compare committed before/candidate renders: only the new ConfigMap and CronJob may appear. Preserve unrelated dirty values and the complete live database Deployment/Pod baseline.
  • Commit and push desired state before Argo reconciliation. Observe an actual scheduled, owner-matched successful Job and durable nonempty archive with matching checksum.
  • Verify the original database Pod UID, Deployment spec, readiness, restarts, existing backups and PVC identities remain unchanged. Do not create a live-only manual Job.
  • A table-of-contents listing and checksum do not prove restore. Complete isolated durable restore and offsite recovery remain required by RECOVERY_PROOF.
  • Rollback removes only the added scheduler/resources through Git. Preserve all real backup generations; never revert data or remove the existing database.

Primary references
