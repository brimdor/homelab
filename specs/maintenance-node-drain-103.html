Research and API contract

The Kubernetes eviction reference defines the policy/v1 Eviction endpoint and normal PDB/grace handling. The exact 1.33.6 API implementation propagates DeleteOptions and honors UID/resourceVersion preconditions; caller-specified resourceVersion prevents its internal conflict retry. The exact kubectl drain implementation does not itself add those identity preconditions. Use the eviction subresource, never force Pod deletion, disable eviction, bypass PDBs or override termination grace.

Implementation and data flow

Add metal/scripts/maintenance_node_drain.py and a focused standard-library test module. Extend only the existing compatible Kubectl.call adapter with optional stdin bytes, retaining secure existing context, fixed command arguments and existing error behavior. No new dependency, credential copy, API proxy, shell command, production CLI or automatic rollout is introduced.

Build a deterministic plan from the exact globally owned, already cordoned Node and every Pod assigned there. Bind namespace/name/UID and complete Pod spec SHA256 plus the exact controlling owner. Verify the current controller exists with that UID. Keep only reviewed actual DaemonSet Pods and actual mirror Pods owned by this same Node; every other controlled Pod is an explicit eviction target. Refuse unmanaged, deleting, foreign or ambiguous objects. No silent omission of Jobs, PVCs or data dependencies. The caller must review the complete plan and prove current recovery, workload/data ownership, availability, capacity and all other prerequisites before starting; the callback is an integration boundary, not substitute evidence.

Commit one drain intent in the existing strict parent journal, bound to the entire reviewed plan and prerequisite SHA256. Keep an immutable private drain side directory outside the numbered parent records. Its header binds the exact parent intent, global/host owners and plan. Each eviction gets its own fsynced0600 intent, including the exact current Pod resourceVersion, before the one actual API POST. Serialize the complete check/intent/POST under the existing native controller flock. Recheck global/host identities, current Node cordon, all current Pod identities/specs and prerequisites immediately before a new eviction. Send both UID and current resourceVersion preconditions; preserve default grace and PDB enforcement.

One call advances at most one eviction or one observation. After a successful, failed or lost API response, keep that micro-intent pending. A fresh controller may only observe that same Pod UID disappearing; if it remains, return pending and never POST it again. Do not classify a transport failure as a definite rejection or retry through another identity. After exact disappearance and current acceptance prerequisites, append an immutable observation bound to the eviction intent, current prerequisite digest and current full target-node inventory digest. Then a later explicit call may begin the next unstarted Pod. Unknown/new target-node Pods, changed owner/spec/UID, corruption, unsafe files or changed global/host ownership refuse.

When every selected Pod has a matching disappearance observation and only the exact reviewed keep-set remains, produce a complete bounded drain receipt binding every side-record hash and current prerequisite digest. Do not automatically accept the parent phase, uncordon, release owners or start packages. The owning controller separately verifies real availability, storage/recovery and application prerequisites before parent acceptance. An interrupted initial header creation may be attached only to the exact existing matching drain intent and unchanged full reviewed inventory, before any eviction could have run. This is explicit recovery, not parent intent replay.
