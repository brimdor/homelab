Research and plan

The official CLI supports --rdb - to stream an RDB snapshot through stdout. Official persistence documentation describes RDB checksums, fork/copy-on-write costs and snapshot consistency. Inspect source memory and persistence health before export. Process one current master at a time; bind exact Pod/PVC/PV/image, source cluster and stable slot topology before/after. Use normal existing CLI access and no configuration or authentication changes. Stream directly through OS pipes and strict existing SSH to a unique root0700 protected point on pikachu; never place real RDB bytes on the workstation or NAS. Hash/fsync0600 files and bind their manifests. Do not overwrite partial or accepted recovery points.

Each shard snapshot is internally consistent. Three sequential shard snapshots are not a cross-shard atomic migration point. Record this limit explicitly. A later data-store migration requires repository-defined writer quiescence and a fresh accepted point; this workflow does not authorize that migration or stop Gitea.

Restore acceptance and cleanup

Pull only the exact running image for an isolated restore. Inspect Linux AMD64 identity, declared volumes and8.1.3 executable. Override the application entrypoint; require uid1001, network-none, no capabilities/host namespaces/devices/ports, read-only root, one exact owned bind and tmpfs. Prove loopback-only routes and no production API route before copying any protected bytes. Verify each original hash, copy only into owned disposable scratch, run valkey-check-rdb and require valid checksum plus parsed key/expiry totals. Start a standalone socket-only server with cluster/AOF/saving disabled. Require exact version, PONG, no external listeners, and loaded-key plus expired-at-load counters accounting for every checked RDB key. Sum keyspace counts and retain expiry limitations: sessions can expire normally after load. Clean shutdown must remove its PID file. Original RDB bytes must remain unchanged.

Tracked finally cleanup removes only exact labelled owned containers, restored scratch and newly fetched images without another consumer; verify absence. Keep original protected points and compact sanitized receipts. No key names, values, RDB content, passwords or raw server logs enter source, reports or transcripts. Unit tests cover source/topology/image/mount refusal, count accounting and error redaction. Validate and publish the workflow on canonical Gitea master before export or restoration. This is a recovery drill, not proof of cluster-wide migration, Gitea login, PostgreSQL recovery or maintenance completion.

Restore socket permission correction

The first protected restore attempt reached RDB checksum validation but did not obtain PONG; its finally cleanup verified container, scratch and newly pulled image removal. This failure does not establish RDB corruption. Valkey8.1.3 config.c declares unixsocketperm default0, which prevents this uid1001 client from using the socket. The isolated server now explicitly selects700 and verifies socket type, uid/gid1001 and exact mode700 after PONG. Production authentication and configuration remain unchanged. Rerun the original protected point after publishing the correction; record success only from actual key accounting and cleanup acceptance.

Server argument correction

The socket correction alone did not establish startup. The exact8.1.3 server argument parser converts separate --name value arguments into configuration directives; it does not implement GNU-style --name=value. Replace every restore-server argument with the native separate form. Run the daemonizing server through attached docker exec so configuration errors are checked immediately instead of being hidden by detached exec. PONG, owner-only socket, data checksum, key accounting and clean shutdown remain mandatory. Neither failed test changed production or the protected original point.
