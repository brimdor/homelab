Research and plan

The official CLI supports --rdb - to stream an RDB snapshot through stdout. Official persistence documentation describes RDB checksums, fork/copy-on-write costs and snapshot consistency. Inspect source memory and persistence health before export. Process one current master at a time; bind exact Pod/PVC/PV/image, source cluster and stable slot topology before/after. Use normal existing CLI access and no configuration or authentication changes. Stream directly through OS pipes and strict existing SSH to a unique root0700 protected point on pikachu; never place real RDB bytes on the workstation or NAS. Hash/fsync0600 files and bind their manifests. Do not overwrite partial or accepted recovery points.

Each shard snapshot is internally consistent. Three sequential shard snapshots are not a cross-shard atomic migration point. Record this limit explicitly. A later data-store migration requires repository-defined writer quiescence and a fresh accepted point; this workflow does not authorize that migration or stop Gitea.

Start a standalone socket-only server with cluster/AOF/saving disabled. Tracked finally cleanup removes only exact labelled owned containers, restored scratch and newly fetched images without another consumer; verify absence. Keep original protected points and compact sanitized receipts. No key names, values, RDB content, passwords or raw server logs enter source, reports or transcripts. Unit tests cover source/topology/image/mount refusal, count accounting and error redaction. Validate and publish the workflow on canonical Gitea master before export or restoration. This is a recovery drill, not proof of cluster-wide migration, Gitea login, PostgreSQL recovery or maintenance completion.
