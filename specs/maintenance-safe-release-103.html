Explicit safe owner release and interrupted observation

Objective and approved scope

A1's published host Hold and Kured Ownership release methods each verify a caller's safety callback. They do not persist a combined release checkpoint. Complete that software boundary under approved Issue103 without releasing any production owner. This component has no production CLI and cannot override missing recovery, NAS restrictions, hardware readiness or application acceptance.

Contract and order

  1. Prepare only after the actual hop journal contains every ordered accepted step with no pending operation, including restored scheduling and application acceptance. Require exact matching owners, host identity/revision, installed guards, idle actors and a fresh verified safety-evidence digest. Persist a private immutable release header binding the original owners and hashes of every complete original hop record before release can start.
  2. Release the native host marker first while the matching global Kured lock remains held. Persist a host-release intent before the existing Hold.release call. Recheck current safety evidence immediately inside its callback. Keep the installed guard drop-ins unchanged. Observe marker absence and exact host identity/guards/idle actors before recording host acceptance.
  3. Release the original Kured owner last, only after proven host-marker release and fresh full safety verification. Persist global-release intent before the existing UID/resourceVersion-tested Ownership.release call. Observe both annotation keys absent on the original healthy Kured controller before recording final acceptance. Never remove a foreign or partially changed owner.
  4. Use the host's existing nonblocking controller flock and private fsynced immutable records throughout. The release header and four optional ordered intent/accepted records form an exact hash chain. Reconstruct after process death or lost response using original record hashes even after the host marker is absent; normal Journal.read correctly requires that marker and is not weakened.
  5. A fresh observer never calls either release operation. If an intended transition is still held, retain pending. If the exact intended absence is observed with fresh accepted safety evidence, append only its observation. No release retry, journal erasure, sentinel deletion, uncordon, package operation or automatic rollback is introduced. Callback refusal, changed host/record/guard/controller/owner or malformed/foreign files remain errors.

Safety evidence and limits

The owning full controller must supply current actual protected affected-data recovery, complete phase acceptance, original scheduling restoration, stable host/boot/release, required GPU/CSI/application behavior, all six healthy layers, idle package/reboot actors and absence of pending reboot sentinels. A callback alone does not establish any of these. This library's tests use explicitly synthetic API/systemd and synthetic phase receipts. Release of two independent owners cannot be one cross-host atomic transaction; keeping Kured until host release is observed preserves reboot exclusion during that ordered interval. Administrators remain able to bypass repository entry points.
