Transition rules and rejected shortcuts

  • Cilium's upgrade guide requires adjacent minor transitions and the latest patch in the current minor first. A future candidate needs every intermediate release's notes, exact immutable artifacts, CRD/value compatibility and preflight results. Do not use a multi-minor leap or --reuse-values to bridge the gap.
  • Keep the initial-version upgradeCompatibility contract and all existing values under review. L7 proxy traffic may disconnect during agent upgrades. DNS, policy allow/deny behavior, API access without kube-proxy, L2 service reachability, Hubble and application connections require separate acceptance after each step.
  • K3s upgrades require consecutive Kubernetes minors, one server at a time before agents, and preserved installation settings. Restarting the installer does not itself drain workloads or preserve omitted flags.
  • Do not downgrade production Kubernetes to fit an old Cilium row. That would require its own supported datastore and binary recovery design; the matrix is not downgrade authorization.
  • Do not combine a CNI transition with Fedora/kernel, GPU, Ceph/CSI or control-plane changes. The Fedora 44 audit and conditional node runbook retain their unresolved package, device and recovery gates.

Isolated qualification implementation — 2026-10-19

Official chart index review isolated-cilium-tool-source-contracts-zf9c7v51 resolves the patched adjacent bridge 1.15.19 → 1.16.19 → 1.17.18 → 1.18.15. First reproduce 1.15.1 on exact k3s 1.33.6, then qualify the current-minor patch and every adjacent minor. This extends the source audit with a test procedure; it does not transform unlisted Kubernetes versions into an upstream guarantee.

cilium_qualification.py accepts only an explicitly named empty Docker VM, a socket inside its private owned workspace, a newly generated loopback-only kubeconfig and exactly three synthetic nodes. It rejects the production cluster UID, any other context/API/version/node set and missing or skipped required test evidence. The caller provides separately checksum-verified official k3d 5.9.0 and Cilium CLI 0.16.24 executables, compatible kubectl, and a private work directory. The k3s image index and all five chart archives are pinned by SHA256 in the helper.

Invoke python3 metal/scripts/cilium_qualification.py with explicit --work-dir, --name qualification-<eight random characters>, --docker-host, --docker-server, --k3d, --cilium and --kubectl. The VM must have no production credentials, source-directory mounts or existing containers. Its owner must finally stop/delete that exact VM, remove all test images, synthetic data, downloaded tools and caches, and retain only compact sanitized evidence.

The helper reproduces kube-proxy replacement, the k3s local API endpoint, L2 announcement enablement, Hubble relay/UI and initial-minor upgrade compatibility. At each stage it requires native agent versions and ready status, then runs official no-policies, ingress-deny, egress-deny and L7 allow/deny scenarios with strict Hubble flow validation. It exercises the preceding Helm revision as a one-minor rollback and then the forward candidate again. JUnit must prove all four required scenarios ran. Failures stop qualification and trigger exact owned-cluster cleanup; an elapsed duration is not a whole-task deadline.

Limits: these connectivity stages alone do not prove production Fedora/kernel/GPU/CSI behavior, physical L2 advertisements or the existing production load-balancer pool. Record the actual VM architecture/kernel and all failures/skips. Add isolated pool/ARP/lease and application traffic evidence before declaring a complete CNI transition candidate. Neither a passing synthetic suite nor this helper authorizes production node disruption.
