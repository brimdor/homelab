Bind firmware work to the installed kernel

Evidence and objective

Cyndaquil returned from its signed Fedora 43-to-44 transaction on 2026-10-27 with kernel 7.2.12-200.fc44.x86_64, boot a6bb6b79-71d7-40e0-927c-0b8dee193310, and no failed units. The existing firmware helper hardcodes 7.2.11-200.fc44.x86_64. Native RPM ownership identifies the new boot image as kernel-core 7.2.12-200.fc44.x86_64; its SHA256 is 7426fed6e7ae1d5db796b339ca87374cf1aa5a7cd0c07feec95e098263536047. The four vendor relabel script hashes remain unchanged. Evidence: maintenance103-cyndaquil44-native-vendor-input-watch-bsco0j68.

Requirements and scope

Issue 103 already authorizes supported Fedora updates and final host security. Keep both observed Fedora 44 kernels available for serial maintenance: 7.2.11 and 7.2.12. Resolve the running kernel from uname, reject every unreviewed version, and verify exact kernel-core ownership of its boot image before selecting its initramfs or invoking dracut. Bind new firmware build, acceptance and reboot records to that kernel. Old records without a kernel field mean only the original 7.2.11 version; they cannot authorize work on 7.2.12.

Implementation plan

  1. Add the bounded kernel resolver to metal/scripts/maintenance_host_security.py and use it for firmware, GDS and final acceptance.
  2. Add focused standard-library unittest cases in metal/scripts/test_maintenance_firmware_kernel.py, following existing explicit assertions and rejected-input tests.
  3. Run the focused firmware, seccomp and Rook hostPath tests; review the exact source diff and run applicable configured pre-commit checks.
  4. Commit and push only these three files to canonical Gitea master before the production controller loads the change. Continue the existing owner without replaying a package transaction or reboot.

Boundaries and rollback

Preserve ownership, recovery, signature, firmware hash, candidate checksum, single-dispatch, reboot and 90-minute OSD protection gates. No package downgrade, broad kernel wildcard, audit suppression, NAS change, storage mutation or next-node work. Revert this source commit for future work if needed; preserve current intents and observe uncertain dispatches instead of replaying them. No new human decision is required for this already-authorized software fix.
