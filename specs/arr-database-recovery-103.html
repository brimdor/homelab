Approved scope: #103 RECOVERY_PROOF. Protect the two application databases, their complete SQLite journals and original configuration through existing strict SSH and protected non-NAS recovery storage. This is database recovery; it does not cover every retained PVC file or NAS media/backups.

Evidence and assumptions

Read-only source inventory1k79tt2q and runtime contracts yjfeilel/28kbjwok on2026-10-20 bind both unchanged Ready zero-restart Pods, their sole Ceph config claim and three separate original NFS mounts. Native applications run UID99/GID100/groups100,1000, with -nobrowser -data=/config. Each container has ten processes: the application plus s6 supervision and one BusyBox process. Freezing only the original container init PID would not stop the database writer.

Capture only config.xml, the application database, logs.db and every existing journal/WAL/SHM companion for those two databases. Do not traverse Backups, media/downloads mounts, images, logs directories or other assets. Those remain explicit coverage gaps. No source SQLite connection or checkpoint is opened by the capture. SQLite WAL must remain with its matching database; see official WAL guidance.

Plan and acceptance tasks

  1. Add a fixed-profile helper and regression tests reusing the already-qualified protected framing, permission, typed SQLite fingerprint and watchdog primitives. Use exact container tasks/PID start identities and executable/UID contracts; refuse unknown or changed tasks. Bind the canonical CSI mount and exclusive Kubernetes consumer before and after capture.
  2. Qualify coordinated multi-process pause/resume on an owned native synthetic process tree first, including cancellation/refusal and independent rescue. Each PID uses its own pidfd and independent bounded resume watchdog. Freeze supervisors before the application, require all threads stopped, recheck the complete task set and resume/reap all owned watchdogs in finally. A failed or over-budget capture produces no accepted stream.
  3. Warm only the selected database files through read-only file I/O before pausing. Re-read fresh identity afterwards. Require actual available RAM for the entire selected capture. Capture the whole selected set to RAM while all source processes are stopped, with no disk/SSH transfer until all original processes have resumed. Preserve complete journals, stable file identities and one shared stopped interval below ten seconds.
  4. Publish the reviewed helper/test/spec candidate to canonical Gitea before touching a live writer. Receive a complete hash-committed stream on existing protected Pikachu storage0700/0600; preserve any uncertain partial.
  5. Open only disposable copied databases for WAL recovery, integrity/FK and full typed schema/metadata/row/rowid multiset fingerprints. Never modify a protected point. Boot a second untouched copy in the exact AMD64 native image with UID99/GID100, no network, privileges, ports, host/NAS mounts or actual provider route. Run the original executable directly, require native readiness and clean shutdown, then fingerprint stopped copies. Report any native startup changes honestly.
  6. Verify original Pod/container/process/image/PVC/PV/mount/exclusive consumer identities and zero restarts after capture. Finally remove exact owned containers, new unused images, copied data, scratch and children; require protected hashes unchanged. Record only aggregate hashes/counts/versions, no credentials or records.

Follow their fail-fast argument-array and exact-identity style. Example: if observed_tasks != reviewed_tasks: raise RuntimeError("container task set changed").

Run scoped tests through the operator's verified disposable environment: python3 -B -m unittest discover -s metal/scripts -p test_arr_database_recovery.py, then pre-commit run --files metal/scripts/arr_database_recovery.py metal/scripts/test_arr_database_recovery.py specs/arr-database-recovery-103.html. Native execution requires explicit namespace/run identifier/manifest SHA and the exact published source bundle, using the existing tracked pipe and finally cleanup pattern.

Boundaries and rollback

Always protect original data and preserve failed evidence. Existing authorization covers independent database recovery work; no new approval gate is introduced here. Explicit application releases, provider actions, destructive data changes and production rollout gates remain separate. Never write NAS/NFS, trigger native backup endpoints, copy real data to disposable workstation storage, reset credentials, mount originals in a test container, downgrade live data or claim public login/media/offsite/all-PVC recovery proof. Capture rollback is unconditional exact-PID resumption; restore rollback is exact owned fixture cleanup. No production chart, Pod, volume or application configuration changes.
