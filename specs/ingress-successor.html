Ingress successor

Maintenance 103, task INGRESS_SUCCESSOR. The owner authorizes autonomous maintenance. This design stages a maintained proxy before any public routing change.

Observed contract

The October 19, 2026 inventory contains 47 Ingress objects and 48 hosts. Existing annotations control request size, Emby buffering/timeouts, and the Kanidm HTTPS backend. The controller also forwards TCP 22 to Gitea. Cloudflared has explicit external routes before its wildcard, which targets the current controller Service. Existing certificates, DNS, application authentication, Service identity and public address must survive.

Selected implementation

Use Traefik OSS Helm chart 42.0.0 and Proxy 3.7.15 pinned by image digest. Enable only its Kubernetes Ingress NGINX compatibility provider, with status publication disabled during parallel validation. Disable the ordinary Ingress, CRD and Gateway providers, dashboard, and Hub features. The new proxy remains in the existing ingress-nginx namespace and Application; a separate ClusterIP Service provides the parallel path. Existing NGINX stays active during acceptance.

Ordered changes and acceptance

  1. Give only the existing ingress Application Helm skipCrds=true through a dedicated Git generator in its current ApplicationSet. Exclude that path from the broad generator. Prove generated paths, names and application UIDs remain identical. The generator template merges only the Helm flag; do not change global templating or the CRD replacement generator.
  2. Add the pinned Traefik dependency alongside NGINX. Prove every existing rendered resource stays unchanged. Deploy the new ClusterIP proxy with a file-provider Gitea SSH route and metrics. Verify all observed HTTP/TLS hosts, backend protocols, redirects, body limits, streaming timeout settings, application authentication boundaries and SSH host identity through the parallel path. Preserve Ingress statuses, public Service UID/address, DNS, TLS and old controller readiness.
  3. After route acceptance, transfer the existing public Service and nginx IngressClass into repository templates with identical identities and initial settings. The old chart ties its publish-service argument to Service creation, so preserve that exact argument through extraArgs. Its argument ordering changes the old controller Pod template; verify the normal rolling replacement, status publication, and public routing before cutover. Switch only the public Service selector and target ports to the accepted proxy. Keep the old controller available until public routing and Gitea SSH pass. Roll back by reverting the exact routing commit through Gitea and Argo.
  4. Retire old NGINX controller, admission and RBAC resources through Git after public acceptance. Preserve the public Service, IngressClass, certificates and existing namespace/Application. Repeat all six health layers and update the issue; incomplete application or network evidence keeps the task open.

It survived chart pruning. Preserve the new monitor, metrics Service and public Service by comparing their UIDs and specifications before and after. This stateless scrape definition has no data or backup requirement. Stop on any changed identity or uncertain write outcome; do not retry a deletion.

Failure handling

Stop the affected phase on route, TLS, authentication, storage, configuration or rollout regression. Do not cut over an unverified proxy. Revert the exact phase commit through GitOps; retain the working NGINX path. No live Ingress edits, manual Helm releases, new probe Pods, copied secrets, paid features, or data migrations are part of this change.
