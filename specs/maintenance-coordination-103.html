Maintenance ownership — A1 prerequisite

Objective and scope

Implement the shared ownership primitive required by maintenance103 before a future in-place OS controller can hold package/reboot actors, cordon, drain or run transactions. Reuse the deployed Kured1.21.0 single-owner protocol, instead of introducing a second unrelated lease. This component acquires, observes and explicitly releases runtime ownership only. It does not change a DaemonSet pod template, packages, host files, Nodes, scheduling, storage or application data. No production acquisition during initial qualification.

The existing maintenance contract authorizes software development and GitOps publication. Source/target and one exact active node are explicit. Production package operations remain blocked by the separately recorded recovery, hardware, compatibility and denied archive gates. This component does not claim those gates passed.

Primary source and design

Exact Kured1.21.0 lock implementation checks a DaemonSet annotation containing nodeID, metadata, created and TTL. TTL0 never expires; a different node cannot acquire until the annotation is removed. Updates use Kubernetes resourceVersion conflict control. Exact main program defaults to concurrency1 and weave.works/kured-node-lock, with node identity from KURED_NODE_ID. A maintenance owner must never equal an actual node name.

Implement metal/scripts/maintenance_coordination.py with the standard library and a supplied compatible kubectl executable. Read the actual DaemonSet and all Pods owned by its exact UID; require the pinned digest, normal node identity, concurrency1/default, default lock annotation and no forced reboot. Refuse deleting, unready, mixed-version or incompletely rolled-out controllers. Compare the actual DaemonSet and each active Pod command/environment; do not assume a chart value describes the running process. Verify expected active node names/UIDs from a caller-supplied exact map.

Acquire only when the Kured annotation is entirely absent and no existing unfinished maintenance journal or node reboot-in-progress annotation exists. Never steal even an apparently expired lock. Use one JSON Patch with tests for DaemonSet UID/resourceVersion and add the Kured lock plus a bounded maintenance journal in the same request. The journal records protocol version, random owner token, selected node/UID, source/target releases, repository revision, creation time and phase. The resourceVersion test protects both initially absent annotations and concurrent owners. Any uncertain response requires observation before another attempt.

Resume reads the persisted journal and exact matching Kured lock, with TTL0, then verifies controller/Pod/Node identities again. It must not create a new token, replay package commands, uncordon or release automatically. A local process exit or network failure leaves the durable ownership intact. Lock acquisition proves Kured exclusion only; dnf-automatic/dnf5-automatic, cron, GPU roles and manual workflows still require separate real holds and native qualification.

Release is an explicit operation after the owning controller's full health and actor-restoration gates, never a finally handler. Require the exact journal token and target identity; require every inventory node Ready, no pressure, no reboot-in-progress annotation and no pending reboot sentinel through an independently verified future host gate. This initial module exposes release only as a library operation with a caller-supplied verification callback; no production release CLI. Invoke the callback immediately before the same UID/resourceVersion/token-tested patch removing both owned annotations. A callback is an integration boundary, not proof that the full cluster or host gate exists.

Commands and structure

Source: metal/scripts/maintenance_coordination.py. Focused tests: metal/scripts/test_maintenance_coordination.py. Native qualification: metal/scripts/qualify_maintenance_coordination.py and metal/maintenance/qualification/kured-owner.go, compiled in an owned exact upstream checkout. Execute python3 -m unittest discover -s metal/scripts -p test_maintenance_coordination.py -v from the approved disposable environment. The initial CLI permits read-only inspection only: python3 metal/scripts/maintenance_coordination.py --kubectl /absolute/compatible/kubectl inspect. Mutations are library operations for the future reviewed in-place controller and qualification harness.

Style and tests

Use explicit ValueError/RuntimeError failures and ordinary dictionaries matching the upstream wire format. One shared validator for acquisition, resume and release. Use a small stateful fake API implementing actual UID/resourceVersion JSON Patch preconditions for unit tests; test simultaneous claim attempts, uncertain writes, controller death/resume, foreign/expired/malformed ownership, changed identities, unsafe runtime flags and release refusal. Add independent qualification against the exact upstream Go lock code and a real API before claiming interoperability or deployment readiness. Unit tests alone cannot certify Kured behavior.

Execution plan and acceptance

  1. Write and review this specification against issue A1, current chart and upstream1.21.0 source.
  2. Implement minimal lock/journal transport and strict running-controller validation; keep host and package operations absent.
  3. Run focused race, refusal and crash/resume tests, static checks and complete diff review. Publish the scoped files to canonical Gitea master.
  4. Qualify exact upstream interoperability in an owned disconnected fixture with cleanup. Record failures honestly; no production lock until the complete actor controller and all affected gates pass.

Boundaries and rollback

Always preserve unknown annotations, all pod templates and exact resource identities. Never steal a Kured lock, auto-expire maintenance ownership, suppress a denial, use force reboot, delete sentinels, reboot a production node, or imply a root administrator is technically fenced from manual commands. Restore only owned runtime annotations after explicit verified release. A Git revert removes code; it does not release a held runtime lock. Keep failed or uncertain ownership for inspected recovery. No new human approval is requested for this already-authorized software work.
