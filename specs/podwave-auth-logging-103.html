PodWave credential logging repair

Maintenance103 / APP_ACCEPTANCE prerequisite and IMMUTABLE_IMAGE_TAGS slice. Plan:2026-10-19.

Evidence

Both running images execute node build/index.js and contain the same compiled login handler SHA256cc2471ecfae1e5c4e318d2b248bacb3db49c42a3c7e847f4a51d3e90ec362cf5. Its Login attempt console call receives the complete submitted credential object. No real login credential was submitted during this investigation. Production data exists on its two existing Ceph claims. Canary has no declared persistence; /app/data and /app/downloads were both empty, PODWAVE_DB unset, and compiled default path is /app/data/podwave.db. Deployed scans found no AuthCheck/session-cookie logger; the newer local upstream hook is not assumed deployed.

Required change

Remove exactly the unsafe console line from the existing final JavaScript artifact. Store the final artifact in each owning chart and overlay only the exact compiled file through a read-only ConfigMap subPath. Pin each existing runtime digest; preserve all authentication logic, cookies, sessions, schema and upstream history. Add separate canary Ceph data/download claims and a no-overlap RollingUpdate strategy (unavailable1, surge0) before its first authenticated acceptance creates data. Preserve production claims and no-overlap rollout.

Verification and rollout

Test the final handler with synthetic credentials for missing fields, invalid credentials, success and a generic database failure. Require identical status/body/cookie/session behavior while no submitted password or session marker reaches logs. Baseline should reproduce the leak. Render/lint both pinned app-template5.0.1 charts and compare every resource; permit only exact image spelling, patch ConfigMap/mount/checksum, and canary persistence/no-overlap strategy additions. Check fresh canary paths remain empty immediately before publication; abort if data appeared. Commit/push canonical Gitea master, reconcile canary first, verify actual patch hash/image/claims/readiness/TLS, then production. Recheck unchanged production PVC/PV identities and read-only database integrity/counts before/after. Credentials stay in RAM and only normal canonical HTTPS auth is allowed. Logout only the created session.

Rollout correction

The first canary commit f6a7f1efdb4f4fdea0f90a49c20e5c91cea07125 was rejected before Pod replacement: server-side apply retained the existing rollingUpdate fields, which Kubernetes forbids alongside Recreate. The old Pod remained Ready. Use the same no-overlap RollingUpdate contract as production (unavailable1, surge0), preserving normal GitOps apply rather than forcing replacement. Fresh empty-data verification is required before the corrected commit.

Recovery and limits

No database migration or replacement binary is introduced. Production retains its existing claims and original image digest. Canary previously has no durable data; newly provisioned claims must be retained after rollback. If data appears before rollout, stop and establish consistent protected recovery before changing canary. Rollback the exact configuration commit through GitOps without deleting claims; restoring the original handler would restore the credential logger, so prefer a corrected overlay. Existing unknown historical credential exposure is not asserted or erased; no raw credential-bearing logs are fetched. NAS writes, registry publication, account resets and Strata changes are outside this repair.
